# 简历诊断：类型化规则（产品设计补充）

> **本文不是调研结论。** 调研原文在 [`docs/resume-rules.md`](./resume-rules.md)，其中 A–E 维度权重、40 条检查项与判定口径均来自该文。本文只解释一件事：**同一条规则落到「实习」和「个人项目」上时，为什么扣分不同、由哪套评分卡计分、哪些结论是产品推断。**
>
> 两份文档冲突时，以调研原文为准；本文新增的类型权重与 R41 属于产品设计，可由人工覆盖。

---

## 1. 为什么要区分经历类型

一份简历里的「经历」不是同一种东西：

- **实习/工作**有公司、同事、上线流程与线上指标，评审者关心的是「你个人做了什么、结果由谁验证」。
- **个人项目**没有同事也没有生产流量，评审者关心的是「你是否工程自觉：压测、边界、取舍、明确没做的部分」。
- **开源、竞赛、课程作业**的边界更特殊：代码可能大部分不是本人写的，成绩也可能属于团队。

如果所有段落都用同一套权重，会出现两个方向的误判：

1. 拿实习的标准要求个人项目（「为什么没有线上监控」），把诚实的小项目判死；
2. 拿个人项目的宽松标准看实习（「有指标就行」），放过「把团队成果写成个人成果」的简历。

因此诊断先切段、再判类型、最后按类型选评分卡。**类型不是隐藏的猜测，而是输入的一部分。**

## 2. 经历类型与识别口径

| 类型 | 含义 | 使用的评分卡 |
| --- | --- | --- |
| `internship` | 实习、全职工作、兼职（有雇主与同事） | 实习评分卡（I1–I5） |
| `personal_project` | 自己发起、自己主导的个人项目 | 个人项目评分卡（P1–P5） |
| `opensource` | 参与开源仓库、给他人项目提交 PR | 个人项目评分卡（P1–P5） |
| `competition` | 学科竞赛、黑客松、比赛作品 | 个人项目评分卡（P1–P5） |
| `coursework` | 课程设计、实验、跟教程完成的练手项目 | 个人项目评分卡（P1–P5） |
| `unknown` | 无法判定或信号冲突 | 不打分，先请用户确认 |

项目类三种（开源 / 竞赛 / 课程）复用个人项目评分卡，是**产品决定**：它们同样缺少生产环境与雇主背书，评审重点都是「边界是否说清、结果是否可验证」。差异体现在扣分上（见第 4 节），而不是另造三套权重。

### 2.1 切段

1. 先按「日期范围行」切段：`2025.06-2025.09`、`2025/6—至今`、`2025 年 6 月 - 2025 年 9 月` 等。
2. 教育相关行（教育、大学、学院、本科、硕士、毕业等）不参与项目切段。
3. 遇到小节标题（项目经历 / 实习经历 / 工作经历 / 技能等）只切换当前段落的归属，不把小节标题本身写进上一段正文，避免「实习经历」四个字污染项目描述。
4. 没有日期时退化为空行分块；再没有则整篇视为一段。

### 2.2 判类型

1. **小节标题优先**：`项目经历` 下的条目默认按个人项目处理，`实习经历 / 工作经历` 下的条目默认按实习处理。标题是作者自己划的边界，比正文里偶然出现的「实习」二字更可靠。
2. 小节内再按关键词细化：项目段若标题明确写了开源、竞赛或课程，分别落到对应类型；否则保持个人项目。
3. 没有小节标题时，对每段做关键词计分：**标题命中 ×2，正文命中 ×1**，取最高分类型；最高分为 0 或最高分与次高分相同 → `unknown`，并返回候选类型。

`type_source` 记录类型来源：`section`（小节标题）、`keyword`（关键词计分）、`user`（用户确认覆盖）。**三者都不会把 `unknown` 静默归类。**

`unknown` 不参与打分，接口返回 `needs_confirm = true` 与 `needs_confirmation` 列表（段落序号、标题、摘要、候选类型）。前端展示为可修改的下拉框；用户改完后带 `segment_types` 重新请求，`type_source` 变为 `"user"`。**用户覆盖优先于关键词判定，且不再要求确认。**

`unknown` 段落在本次结果中 `score = -1`，不参与加权总分；只有全部段落都未知时，总分退回文档分（research rubric）。

## 3. 两套评分卡与 A–E 的映射

调研评分卡（文档级，固定不变）：

| 维度 | 名称 | 权重 |
| --- | --- | --- |
| A | 真实性与可验证性 | 30 |
| B | 量化质量与结果 | 25 |
| C | 结构与表达 | 15 |
| D | 岗位匹配与技术深度 | 20 |
| E | 格式与细节 | 10 |

类型化评分卡（段级，两种）：

| 实习 `internship` | 权重 | 个人项目 `personal_project` | 权重 |
| --- | --- | --- | --- |
| I1 真实性与边界 | 35 | P1 工程自觉 | 35 |
| I2 结果与影响 | 30 | P2 可验证性 | 25 |
| I3 岗位匹配 | 20 | P3 技术深度 | 20 |
| I4 结构表达 | 10 | P4 结构表达 | 15 |
| I5 格式 | 5 | P5 格式 | 5 |

映射关系（同一条规则命中后，扣分落到哪一维）：

| 调研维度 | 实习 | 个人项目 | 映射理由 |
| --- | --- | --- | --- |
| A 真实性与可验证性 | I1 真实性与边界 | P2 可验证性 | 实习看「是不是你做的、边界在哪」；个人项目看「能不能验证」 |
| B 量化质量与结果 | I2 结果与影响 | P1 工程自觉 | 实习结果进入业务指标；个人项目量化更看是否主动做压测与复盘 |
| C 结构与表达 | I4 结构表达 | P4 结构表达 | 两种场景都看信息密度与结论先行 |
| D 岗位匹配与技术深度 | I3 岗位匹配 | P3 技术深度 | 实习重岗位对齐；个人项目重技术选型与深度 |
| E 格式与细节 | I5 格式 | P5 格式 | 一致 |

### 3.1 计分公式

**文档分（research rubric）**

```
文档分 = 100 − Σ命中扣分
```

- 每个维度的扣分不超过该维度权重（A 最多扣 30，B 最多扣 25，以此类推）。
- 维度得分为 `权重 − 该维扣分`，最低 0。
- 文档分最低 0。

**红线**

命中任一 `redline` 规则时：

- A 维直接清零（扣满 30）；
- 文档分上限 69，即使其它维度没有扣分也不会超过 69；
- 加权总分同样封顶 69，避免出现「命中红线但总分落在 4 档」的自相矛盾；
- 段级评分仍然按类型正常计算，便于用户看到「哪段有问题」。

**段分（typed rubric）**

```
段分 = 100 − Σ映射后的扣分
```

- 同样按类型化维度设上限（例如 P1 最多扣 35）。
- 段分最低 0；`unknown` 段记为 −1，不参与加权。

**总分**

- 以段落正文字数（不足 40 字按 40 计）为权重，对已完成类型的段分做加权平均；
- 没有任何可计分段时，总分退回文档分，`weighted = false`。

这样做的代价是：**同一段文字换个类型，段分和总分都会变**。这是有意的——实习与个人项目本来就不该用同一把尺子。可预期性由 `type_source` 与逐段展开的维度扣分保证。

**为什么个人项目在 R03/R04/R08/R09/R41 上扣得更重**：这些规则指向「用远超实际投入的规模词包装一个小项目」。实习至少有公司流程可以解释规模；个人项目没有这层背书，夸大的落差更直接，所以扣分更重。这是产品判断，不是调研原文的量化结论。

### 4.1 证据强度标签

| 标签 | 含义 | 在系统中的用法 |
| --- | --- | --- |
| `strong` | 调研中有明确依据，且可由文本直接判定 | 正常自动扣分 |
| `medium` | 调研有依据，但需要一定语义判断 | 自动判定为「疑似」，提示人工复核 |
| `single` | 仅单一来源或样本，属于经验性规则 | 扣分较轻，可人工覆盖 |
| `inference` | 调研中没有直接结论，由产品推导 | **标注「产品推断，可人工覆盖」，扣分可在规则文件中调整** |

`inference` 目前有两条：R11（仓库量级与描述不符，纯人工）与 R41（课程/教程项目包装成生产系统）。两者的阈值都不是调研给出的数字。

### 4.2 三种执行模式

| 模式 | 含义 | 计分方式 |
| --- | --- | --- |
| `auto` | 机器可判 | 命中即按规则扣分 |
| `auto_manual` | 机器只能判一部分 | 按 `auto_ratio`（当前 0.5）先扣一半，剩余进入「需人工确认」 |
| `manual` | 纯语义/版式判断 | 不自动扣分，列在 `manual_checks` |

`auto_manual` 的剩余分不会凭空扣掉：响应里会明确写「自动判定覆盖 X 分，剩余 Y 分需人工确认」。这样既不让机器替人做语义裁决，也不假装规则已经覆盖全部。

纯人工项当前有 9 条：R11、R19、R21、R24、R25、R29、R30、R35、R37。它们出现在 `manual_checks`，标注「需人工确认」。

## 5. 反向规则：落差检测

正向规则问「有没有写结果」；反向规则问「写的结果是否撑得住宣称」。按落差类型分组：

| 落差类型 | 规则 | 触发信号 | 证据 |
| --- | --- | --- | --- | 
| 宣称与佐证落差 | R05、R06、R07、R10 | 「主导/独立/从 0 到 1」但没有团队规模、模块边界、部署方式或可核验产出 | strong / medium |
| 周期与栈矛盾 | R03、R04 | 三周项目写分布式；三个月项目堆 8 项以上中间件 | medium（调研明确列为高频包装） |
| 量级无佐证 | R08、R09、R20 | 99.99%、百万用户、P99 降 80%，但没有基线、环境、数据量或来源 | strong / medium |
| 职级与分工越界 | R12、R05、R06、R27 | 应届生写架构师/技术负责人；全篇强动词 | medium / strong |
| 教程项目伪装生产系统 | R41 | 「企业级/高可用/生产级」+ 课程、教程、跟练等来源线索 | inference（产品推断） |

其中 **R03、R09、R12、R21 为红线**：命中后 A 维清零、文档分封顶 69。红线不追求「精确扣分」，而是明确告诉用户「这条不改，简历会在一面被直接质疑」。

「三周完成分布式电商」会被 R03 直接命中：`reShortPeriod` 识别「三周/3 周/一个月」，`reScopeClaim` 识别「分布式/高并发/多租户/容灾」；若同段又写「从 0 到 1/主导/架构师」，R05/R12 会继续叠加，但维度扣分有上限，不会出现负分。

## 6. 诚实标注：不扣分，也不加分

以下词被视为「诚实边界」，命中后**抑制对应规则**：

| 标注 | 抑制的规则 | 说明 |
| --- | --- | --- |
| 单机部署、单机、测试机、本地压测、未上线、未对外、未公网、小规模内测、内测 | R07（声称上线却无部署）、R09（量级无佐证） | 说清部署范围就不算「假装生产」 |
| 方案设计未落地、未落地、仅方案、规划中、课程了解 | R03（短周期大宣称）、R41（教程项目伪装生产） | 明确「没落地」就不再按落地项目要求 |
| 未统计、未做多副本 | 量级/可用性相关判定 | 承认没统计，比编一个数字可信 |

规则是**只减不加**：诚实标注不会获得额外加分，只是避免被误判。原因是加分会让「写免责声明」变成刷分技巧；而不扣分已经足够保护诚实描述。

对应地，产品态度写进了 [`design-rationale.md`](./design-rationale.md) 的「toy 不是罪，装作不是 toy 才是」一节：小项目本身不是问题，把小项目说成生产系统才是问题。

## 7. 两个读者，两个分数

同一份简历，HR 与面试官看的东西不同，因此分别给分，不合并成一个「总评」：

### 7.1 `screen_score`（HR 初筛视角）

| 组成 | 权重 | 口径 |
| --- | --- | --- |
| JD 关键词覆盖 | 40% | 从 JD / 目标岗位抽取关键词，统计正文命中率；无 JD 时按满分 |
| 技术词密度 | 20% | 识别到的技术栈数量 × 15，封顶 100 |
| 岗位匹配 | 20% | 目标岗位或方向词是否出现在前 300 字 |
| 篇幅与结构 | 20% | 常见小节数量；正文 < 400 字或 > 6000 字扣分 |

### 7.2 `tech_score`（面试官视角）

| 组成 | 权重 | 口径 |
| --- | --- | --- |
| 主张可自证 | 40% | 条目中含数字、单位、链接、压测、监控等可核验信号的比例 |
| 指标有基线 | 25% | 同时给出基线（从 X 到 Y / 版本对比）与环境（机器、数据量、并发）的性能指标比例 |
| 职责边界 | 20% | 写明团队规模、模块边界、review 机制的段落比例 |
| 三层追问韧性 | 15% | 提到取舍、限制、失败分支或「明确没做」的段落比例 |

### 7.3 分数冲突时给建议

- `screen − tech ≥ 15`：初筛友好但证据偏弱，二面容易被追问打穿；优先补基线、环境与个人边界。
- `tech − screen ≥ 15`：证据扎实但关键词覆盖不足，可能被 HR 过滤；按 JD 前三关键词补技能栏与项目描述。
- 差值 < 15：未发现明显错位。

这两个分数**不替代**文档分与段分：文档分回答「按调研规则扣了多少」，段分回答「这段经历在它自己的类型下值多少」，screen/tech 回答「两个读者分别会不会放行」。

## 8. 五档与追问

| 档位 | 分数 | 含义 |
| --- | --- | --- |
| 1 档 | 0–39 | 无法通过初筛：造假/职级错位，或全篇无结果、无数据、无边界 |
| 2 档 | 40–54 | 表述空泛：有项目但只有负责/参与，缺 before→after |
| 3 档 | 55–69 | 基本完整：项目真实、结构完整，但量化口径不严 |
| 4 档 | 70–84 | 可信清晰：有可信指标与边界，仅有少量细节扣分 |
| 5 档 | 85–100 | 可直接投递：每条经历能讲 5 分钟，指标有分母/环境/来源 |

每段经历附带与该类型绑定的追问模板（节选）：

- **实习**：改动落在哪几个文件/哪几行？上线后哪个指标动了、谁统计？谁 review 了你的代码？出过什么事故？
- **个人项目**：用户量 ×100 先崩在哪？压测的数据量/并发/机器规格？为什么选 X 不选 Y？哪些明确没做？
- **开源**：PR 解决了什么问题、维护者提了什么意见？如何验证兼容性？最后合入了吗？
- **竞赛**：你负责哪一部分？方案卡在哪、怎么取舍？名次与参赛队伍数量？
- **课程**：课程要求还是主动扩展？代码量多少、哪些是框架给的？独立重写会先改哪里？离生产还差什么？

追问的作用是检验分数：`tech_score` 高但答不上「基线/环境/边界」，说明简历写得好而经历经不起追问。

## 9. 接口契约

`POST /v1/resume/analyze`

请求：

```json
{
  "text": "简历全文",
  "jd_text": "岗位 JD（可选）",
  "target_role": "Go 后端开发工程师（可选）",
  "filename": "张三-Go后端.pdf（可选）",
  "segment_types": [{ "index": 0, "type": "internship" }]
}
```

`segment_types` 只用于用户确认/覆盖；索引越界或非法类型返回 400；`type` 不允许为 `unknown`。

响应要点：

| 字段 | 含义 |
| --- | --- |
| `overall_score` / `band` | 加权总分与五档 |
| `document_score` | 调研 rubric 文档分（100 − Σ扣分，红线封顶 69） |
| `weighted` | 是否使用了段级加权（全部 unknown 时为 false） |
| `screen_score` / `tech_score` | 两个读者视角的分数与组成项 |
| `conflict_advice` | 两分冲突时的建议 |
| `dimensions` | A–E 每维权重、扣分、得分 |
| `segments` | 每段的类型、来源（section / keyword / user）、月数、权重占比、段分、类型化维度、追问模板 |
| `issues` | 每条命中的规则 ID、维度、严重度、证据强度、扣分、原文引用、改写示例 |
| `manual_checks` | 纯人工项与 auto_manual 的剩余分 |
| `needs_confirmation` | 未知类型的段落、摘要、候选类型 |
| `redline` / `model_called` / `rule_hits` | 是否触发红线、是否调用模型（恒为 false）、命中条数 |

`model_called` 恒为 `false`：这条链路只读文本、只跑规则，不访问网络。

## 10. 已知限制

1. **纯文本输入**：页数（R29）、版式与 ATS 兼容性（R30）、文件命名（R37）无法从文本判定，只能列入人工确认。
2. **语义边界**：R24/R25/R35 等需要理解「取舍是否成立」，机器只给提示，不替用户下结论。
3. **关键词判定有偏差**：类型识别是关键词计分，标题写法特殊时可能落到 `unknown`；这是有意选择「宁可问、不猜」。
4. **不调用模型**：所有分数可离线复算；代价是对反讽、隐喻、跨段指代不敏感。
5. **类型化权重是产品推断**：35/30/20/10/5 与 35/25/20/15/5 没有调研样本支撑，后续可按真实反馈调整，调整只改 `rules/checks.yaml`，不动代码。
