# 设计取舍

这份文档回答一个问题：**这些地方为什么这么写，代价是什么，如果换成另一种常见做法会发生什么。**

不是功能清单，也不是架构介绍。每条取舍都按「选择 / 为什么 / 代价 / 换一种做法会怎样」展开，方便评审时直接质疑。

---

## 1. 回合制短图，而不是一场面试一个大图

**选择**：作答链路的 `compose.Graph` 只覆盖一个回合：`snapshot → evaluate → decide → ask`。面试的循环由应用层按「提交一次答案 = 执行一次 run」反复驱动，而不是把整场面试编进一张长图。

**为什么**：

- 一次 HTTP 请求只承担一个回合的工作量，超时、重试和失败边界清晰。
- 每个回合结束后状态已经落库，进程崩溃最多损失当前回合，不会丢掉整场会话。
- 图小，改一处评估节点不需要重新理解整场面试的控制流。

**代价**：循环控制、停止条件和跨回合状态由应用层自己维护，`internal/app/runner.go` 变厚；单看 agent 层看不到「面试如何结束」，需要结合决策门一起读。

**换一种做法会怎样**：把整场面试做成一张大图（循环边 + 全局状态），图框架负责循环与 checkpoint。代价是图的节点和边会随追问、收尾、重试迅速膨胀，单次执行时间变长，任何一次模型超时都要重放整条链路；调试时也很难只复现「某一题为什么追问」。

---

## 2. 自管步骤日志，而不是依赖框架 checkpoint

**选择**：用 `runs` / `run_steps` 表记录每个节点的输入摘要、输出产物和状态，崩溃恢复时从最后一个成功节点续跑。eino 只作为模型与图编排库，不把它的 checkpoint 当作恢复事实源。

**为什么**：

- 恢复所需的信息必须和业务数据在同一个事务边界里。`run_steps` 与 `turns`、评估记录同库同事务，恢复点不会和业务状态打架。
- 步骤日志本身就是可观测数据：重试次数、失败原因、耗时、token 都在里面，出问题不需要再去框架内部翻状态。
- 换模型 provider 或升级框架版本时，恢复语义不变。

**代价**：要自己设计步骤幂等（同一节点重放不能重复写 turn、重复发事件），也要自己维护 `running / interrupted / succeeded / failed` 的状态机；框架升级带来的免费能力用不上。

**换一种做法会怎样**：直接用框架 checkpoint，恢复逻辑看起来更省事。但 checkpoint 的粒度和持久化位置由框架决定，往往和业务事务不在一个库、一个事务里；一旦 checkpoint 与 `turns` 写入之间崩溃，就会出现「框架认为完成了、业务表里没有」的分裂状态，排查成本远高于自己写一张步骤表。

## 3. 控制面 POST / 数据面 SSE

**选择**：所有改变状态的命令走 `POST`（创建、开始、作答、中止、收尾、重试），返回 `202 + run_id`；进度与结果通过 `GET /events` 的 SSE 推送。SSE 只读，不承载命令。

**为什么**：

- 命令需要幂等键、鉴权、事务和明确的错误码，这些都属于普通 HTTP 请求；把命令塞进 SSE 会让重连、重放和错误处理都变得含糊。
- SSE 是单向广播，天然适合「服务端推进度」，浏览器 `EventSource` 自带重连和 `Last-Event-ID`。
- 控制面和数据面分离后，前端可以先拿 `run_id`，再独立订阅事件，不需要维持一个长连接来发命令。

**代价**：客户端要处理「命令已返回、事件还没到」的中间态，并按 `event_id` 去重；服务端要额外维护事件表和续播游标。

**换一种做法会怎样**：用 WebSocket 双向通信，看起来一个连接解决所有问题。但双向连接要自己做消息确认、重连后的状态对齐和背压；对「提交一次答案、看一段进度」这种非对称交互，复杂度明显高于收益。纯轮询则实现最简单，但实时性和请求放大会同时变差。

## 4. 规则优先于模型建议

**选择**：追问与停止由 `internal/domain/followup` 的规则链裁决：硬预算门（超时、题纲耗尽、追问总数、深度、单题追问数、不会回答、评估降级）→ 覆盖门（期望点是否覆盖）→ 模型建议 → 终裁。模型只能建议，不能决定是否继续。

**为什么**：

- 预算是产品约束，不是模型可以临时放宽的东西。让模型决定「再来一题」等于把成本和时长交给概率。
- 规则是确定性的，可以单测；模型输出不稳定时，面试仍然能按预算收敛。
- 降级路径明确：评估失败就进下一题，不会因为模型抖动卡死。

**代价**：规则优先意味着有些「模型觉得值得深挖」的回答会被预算截断，体验上不如纯模型驱动灵活；新增规则要同时改门槛、文档和测试。

**换一种做法会怎样**：完全让模型决定追问和收尾。短期体验更自然，但同一份简历可能问 5 题也可能问 20 题，成本和时长不可预测；模型一旦持续认为「还能追问」，会话就没有确定的终点。把预算交给提示词约束也不可靠，模型并不擅长稳定执行计数。

## 5. 分数由确定性评估给出，模型只写点评

**选择**：维度分、加减分、总分、等级全部由 `internal/domain/evaluation` 的确定性代码计算；模型负责打分证据和文字点评，报告里的分数不从模型输出里取。

**为什么**：

- 同一份评估记录必须能复算出同一个分数，否则回归集、门槛和报告都无法比较。
- 报告模型擅长写「哪里好、哪里弱」，不擅长稳定地做算术和跨题汇总；让它算总分容易前后矛盾。
- 分数与点评分离后，换报告模型不会改变分数，反之亦然。

**代价**：模型对「整体印象」的判断无法直接体现在总分上，只能通过维度分和加减分间接表达；规则算出来的分数有时显得比人更机械。

**换一种做法会怎样**：让模型直接给总分和等级。实现最快，但同一答案两次调用可能给出不同等级，M6 的 band 命中率就失去意义；报告里还可能出现「维度分平均 3.2、总分 85」这类自相矛盾。用模型打分再用规则校验，本质上还是把不确定性留在链路里。

## 6. 三重幂等：幂等键、唯一约束、状态机

**选择**：同一业务命令的重复提交在三层被拦住：

1. `Idempotency-Key` 快路径：同一 key 只产生一个 run，重复请求返回原 `run_id` 并带 `Idempotent-Replayed: true`。
2. 数据库唯一约束：`turns (session_id, seq)`、报告唯一键等，保证即使并发绕过快路径也不会写出第二份。
3. 状态机：`answered` 的 turn 不能再次作答，`completed` 的会话不能再次收尾。

**为什么**：

- 网络重试、客户端双击、SSE 重连后的补偿提交都是常态，只靠一层挡不住并发。
- 快路径负责体验（不重复调用模型），唯一约束负责正确性（不重复落库），状态机负责业务语义（不允许的动作直接拒绝）。
- 三层各自独立，任意一层失效时其余两层仍能兜底。

**代价**：每次新增命令都要想清楚幂等键范围、唯一键和合法状态迁移；错误码要区分「重复但等价」和「状态冲突」，前端也要分别处理。

**换一种做法会怎样**：只做幂等键缓存（例如 Redis SETNX）。缓存过期或 Redis 抖动后，重复请求就会穿透到模型和数据库；只靠数据库唯一约束则重复请求会先花掉一次模型调用再失败，成本不可控。三层都省掉，就是最典型的「刷新一下扣两次款」。

## 7. 锁 + PostgreSQL 约束双保险

**选择**：跨实例会话互斥用 Redis `SET NX PX` + token 比较释放；即使拿到锁，写入仍受 PostgreSQL 唯一约束和状态机保护。Redis 不可达时回退进程内锁，并在启动日志告警。

**为什么**：

- 锁只解决「同一时刻谁来执行」，不解决「执行结果是否唯一」。锁可能过期、可能被误释放，正确性最终要落到数据库。
- Redis 锁延迟低，适合挡住绝大多数并发；PostgreSQL 约束是最后的事实源，不依赖外部可用性。
- 回退进程内锁让单实例本地开发不因 Redis 缺失而不可用，同时用告警明确它的适用边界。

**代价**：多了一层依赖和一套锁语义测试（互斥、重入、过期、误释放）；回退模式只保证单实例正确，部署时必须知道这一点。

**换一种做法会怎样**：只用 PostgreSQL advisory lock，少一个组件，但每次抢锁都要占数据库连接，高并发下会把连接池拖垮；只用 Redis 锁，Redis 故障或锁过期时会出现两个实例同时处理同一会话。把「锁即正确性」当假设，是分布式系统里最常见的错误之一。

## 7.1 教训：锁 TTL 必须匹配它的持有时长

**核实结论**：`LOCK_TTL` 默认 10s，而报告生成、真实模型评估可能远超 10s。生产 worker 路径下命令入队后立即释放锁，run 在锁外执行，所以锁不会在 run 期间过期，也不存在「锁过期后两个请求同时改同一 session」；同一会话只跑一个 run 由数据库的 `Claim` 约束与 CAS 兜底。但同步内联执行模式下 run 在锁内执行，10s TTL 会让锁中途失效，此时第二个命令可以拿锁进入，锁的互斥承诺静默失效。这是真实存在的隐患，只是当前默认装配不触发。

**修复**：`ports.Locker` 增加 `Refresh`（仅当前 token 可续期，失去所有权返回 `ErrLockBusy`）；同步内联路径启动 watchdog，按 `LOCK_TTL/3` 续期，失去所有权时记录 `session lock lost during inline run`。测试用 150ms TTL + 600ms run 证明长任务期间第二个 token 拿不到锁。

**教训**：锁的 TTL 要和临界区长度绑定。临界区长度会随执行模式（内联 / 异步 / worker）变化，锁的语义也随之静默改变，所以「锁覆盖到哪」必须写成显式约束并配测试，不能只看默认 TTL 是否够大。

## 8. 可观测性与成本口径

**选择**：每次模型调用都记录 provider、模型名、prompt 版本、尝试次数、prompt/completion token、耗时和失败分类；`/metrics` 暴露请求量、run 结果、模型调用与 token 计数。报告和回归结果都带这些字段。

**为什么**：

- 这个系统的成本几乎全在模型调用上，没有 token 口径就无法判断一次改动是「变好」还是「变贵」。
- 失败要能分类：传输错误可重试，输出不合法走修复，修复超预算才降级；三类问题的处理方式和告警完全不同。
- prompt 版本随评估记录落库，回归结果才能说清「这 60 条是哪个 prompt 跑的」。

**代价**：埋点会侵入模型调用链（`llm/instrument.go`），新增指标要同时维护命名和测试；token 统计依赖 provider 返回值，流式或自建服务可能拿不到精确值。

**链路标识**：`trace_id` 是端到端根，`request_id` 是单次请求分支；客户端不发 trace 头时两者相同，显式透传 `X-Trace-Id` 时表现为父子。`trace_id` 随 run 落库，worker claim 与重试都能恢复，HTTP、节点、模型、工具、事件日志统一出现。先不引 OTel SDK / collector：按 trace_id grep 日志已能还原链路，额外组件换不来当前规模下的新信息；需要时配置 `OTLP_ENDPOINT` 直接发 OTLP/HTTP JSON（无 SDK、无 collector），未配置时零依赖、零网络。

**换一种做法会怎样**：只记录成功/失败，不记 token 和版本。系统照样能跑，但回归集无法解释指标变化，成本只能靠账单倒推；线上出现「变慢」时也分不清是模型慢、重试多，还是锁等待。用第三方 APM 全覆盖则引入额外依赖，且模型语义（prompt 版本、token）仍需自己补。

## 9. depth 维度的可执行锚点

`depth` 是最容易被模型打「印象分」的维度：回答听起来专业，但可能只背了结论。`eval-v4` 起，prompt 与本文档统一使用下面这组可核对定义：

| 分值 | 可执行定义 |
| --- | --- |
| 5 | 机制 + 边界 + 取舍 + 验证，四项齐备；每项至少一句可定位原文，不要求展开成段 |
| 4 | 取舍成立，且边界或验证至少有一项；另一项缺失或只提一句 |
| 3 | 无取舍，或边界与验证都缺；机制只覆盖局部环节 |
| 2 | 只有结论或只背定义，几乎没有机制 |
| 1 | 结论错误、答非所问或纯名词堆砌 |

四要素的判定：机制 = 内部结构/控制流；边界 = 前提、失效条件、异常路径或参数边界；取舍 = 在两个可行做法间做选择并说明为什么不选另一个（只并列方案、只列补救措施不算）；验证 = 基线 + 指标 + 窗口/来源，或实验/线上结果（只提监控/trace/pprof/gcflags 不算）。

硬上限：无取舍 → 最高 3；无边界 → 最高 4；无验证 → 最高 4；边界与验证都无 → 最高 3。

非 `depth` 维度统一使用 1-5 档（`eval-v4` 补齐 2/4）：1 = 明显错误/几乎无信息；2 = 方向对但只有零散片段、无法核验；3 = 基本正确但泛泛而谈；4 = 接近 5 但明确缺一项；5 = 锚点全部满足且可继续追问。5 分锚点按维度拆开：`correctness` 允许没有取舍，`structure` / `evidence` 不要求取舍。

## 10. 为什么不代投（M16）

**选择**：只做 JD 解析、匹配、题纲与申请材料生成，明确不做自动投递；不提供表单自动填写、不批量提交、不保存他人招聘平台账号。

**为什么**：

- **平台协议与个人信息合规**：Boss 直聘等平台的用户协议普遍禁止自动化操作与账号共享，代投会把合规风险转嫁给用户；简历与账号属于个人信息，托管他人账号意味着额外的数据安全责任。
- **各家公司表单结构不可泛化**：ATS 的表单字段、必填项、附件格式与反爬策略各不相同，靠一套脚本覆盖只会产生大量半成功提交，维护成本高于人工确认。
- **代投会掩盖匹配问题**：批量投递制造「投了很多」的错觉，却绕过了逐岗核对 JD 与简历缺口这一步；匹配度与缺口清单才是这个产品真正要暴露的信息。

**代价**：用户仍需自己在目标平台完成投递，产品价值从「帮你投」收窄为「帮你判断该不该投、怎么讲」。

**换一种做法会怎样**：接浏览器自动化或平台接口代投，短期演示效果更炫；但一旦触发风控、封号或信息泄露，产品就从「面试教练」变成「账号代运营」，与原目标不符。

## 11. toy 不是罪，装作不是 toy 才是

**选择**：简历诊断先给每段经历判类型（实习 / 个人项目 / 开源 / 竞赛 / 课程），类型不明就返回候选让用户确认；课程项目、单机部署、小规模内测、方案未落地这些「小」的事实本身不扣分，只有把它们包装成生产系统时才扣分（R41、R07、R09）。诚实标注只免扣、不加分。

**为什么**：

- 学生简历的绝大多数项目本来就是玩具：课程作业、跟教程练手、几十人的内测。用一个「生产系统」的尺子去量，只会逼用户编造规模和指标，诊断也就失去了识别包装的作用。
- 真正该拦的是落差，而不是规模：三周写出「分布式高可用」、课程项目写成「企业级生产系统」、没统计却写 99.99%——这些才是面试官一追问就露馅的地方。
- 诚实标注不加分，是为了防止「写免责声明」变成刷分技巧。承认「未上线、未统计」已经比编数字可信，但可信不等于优秀，分数仍应由可验证的结果与边界决定。
- 类型化评分卡（实习 35/30/20/10/5，个人项目 35/25/20/15/5）让同一段文字在两种身份下得到不同评价：实习看业务结果与个人边界，个人项目看工程自觉与可验证性。

**代价**：类型判定需要用户确认，多一步交互；同一段文字换类型后分数会变，用户可能觉得「不稳定」。我们用 `type_source`（section / keyword / user）和逐段维度扣分把原因摊开，而不是隐藏成单一总分。

**换一种做法会怎样**：统一用一套「生产系统」标准，实现最简单，但会把诚实的小项目判成 1 档，同时放过「小项目吹成大系统」的简历；反过来全部宽松，则实习里「把团队成果写成个人成果」也会漏掉。两种都会让诊断从「识别包装」退化成「按规模打分」。

## 12. 领域包可插拔（M14）

**选择**：把题纲与评分维度外置成带版本的领域包（`domainpacks/<id>/manifest.yaml`），启动时强校验；技术三包（Go / Java / AI Agent）完整可跑，非技术岗位只提供示例包与设计文档，不默认加载。

**为什么**：

- **本地骨架是评分唯一依据**：维度和考点必须离线可跑、可单测、可 diff；评分链路不依赖任何网络内容，面试不会因为抓取失败而停摆。
- **维度不该写死在代码里**：售前看需求理解与异议处理，运营看指标口径与实验设计，硬编码的五维会把所有岗位都量成同一把尺子。维度名、权重随包进入 prompt、校验、报告和 UI，换包不需要改代码。
- **包边界也是可信边界**：`source = curated` 的考点禁止带 URL，`retrieved` 必须带 URL 与抓取时间；未审核内容不会因为「看起来很有用」混进评分。`docs/domainpacks/examples/` 下的示例只展示格式，不参与加载与校验。
- **启动失败优于静默跳过**：包写错（权重不为一、id 与目录不一致、expected_points 不足 3 条）直接报错，避免线上跑着一个维度权重错位的面试。

**代价**：每个新岗位要写 manifest 并过校验，比改代码常量麻烦；不同包的维度不同，跨岗位的分数不能直接横向比较。

**换一种做法会怎样**：把所有岗位的题纲和五维继续写在 Go 常量里。上线最快，但新增岗位要改代码、重新发版，评分维度也无法表达岗位差异；把未审核的网络内容直接塞进题纲，则会让面试问题随抓取结果漂移，回归集失去意义。

---

## 13. 一句话总结

这套系统的取舍主线是：**把不确定的东西（模型）限制在「建议 + 文字」的位置，把确定的东西（状态、预算、分数、幂等、恢复）留在可测试、可复算的代码与数据库里。** 代价是应用层更厚、规则更多；收益是任何一次失败都能定位到具体层，任何一次重复请求都不会产生第二份事实。

## 附录：开发环境注意事项

- **换行符与 CI**：CI 在 Linux 上跑 `gofmt -l .`，判定基准是 LF。Windows 工作区默认以 CRLF 检出时，`gofmt -l` 会把大量文件误报为未格式化，掩盖真正的格式问题。仓库用 `.gitattributes` 固定 `*.go text eol=lf`，本地必须按 LF 复现 CI 结果；这是实际踩过的坑。
- **gofmt 失败先看 diff**：CI 的 gofmt 步骤在失败时先执行 `gofmt -d .` 打印差异再退出，避免只看到一个文件名却不知道差在哪。
- **复现 CI 的环境变量**：单测与 heuristic 回归显式设置 `MODEL_PROVIDER=heuristic`、`OPENAI_API_KEY=""`、`OPENAI_BASE_URL=""`；集成测试用本地 Docker 的 PostgreSQL（宿主 5433）与 Redis（宿主 6380），映射到工作流里的 5432 / 6379 服务名。
