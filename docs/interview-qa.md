# 面试问答速记

面向本人复习。用法：先看问题，自己答一遍，再对照「一句话结论 + 支撑点」。答案只保留能背下来的骨架，细节回 [拆解读物](project-walkthrough.md) 或代码。

覆盖顺序与 [拆解读物](project-walkthrough.md) 一致。最后更新：2026-11-07。

---

## 1. 入口、分层与边界

**Q1：为什么 handler 不直接调数据库？**
一句话：handler 只做 HTTP 语义，业务与存储各有边界。
- 参数校验、异步 run、事件流都在 `app.Service` 编排；
- 存储实现通过 `ports.Store` 替换，测试用内存实现；
- 换 Postgres 以外实现时，`api` 与 `app` 不用动。

**Q2：为什么不用依赖注入框架？**
一句话：依赖数量还在人工可读范围，`main.go` 显式装配更透明。
- 装配点集中，启动顺序（迁移、对账、worker）一眼可见；
- 少一层反射/容器，排错简单；
- 代价是 `main.go` 会变长，超过一定规模再考虑拆分。

**Q3：Redis 挂了服务为什么还能起？**
一句话：Redis 不是正确性依赖。
- 锁 `Ping` 失败回退进程内锁，只保证单实例安全；
- 限流 fail-open，放行并打 `WARN` + 指标；
- 队列、run、事件都在 PostgreSQL，不在 Redis。

## 2. 鉴权与用户隔离

**Q1：为什么 demo 匿名还能隔离？**
一句话：匿名不等于共享账号，每次 demo 都是独立用户。
- `auth.Service.Demo` 每次创建 `demo_<ULID>`，JWT 带独立 `user_id`；
- 所有资源查询按 owner 过滤，跨账号统一 404；
- 登录入口按 IP 限流，业务动作按 demo 更严格额度走 Redis。

**Q2：跨账号为什么返回 404 而不是 403？**
一句话：404 把「不存在」和「无权」合并，少一个枚举面。
- 403 等于承认资源存在；
- 资源归属检查失败统一转 `ErrNotFound`；
- SSE 订阅前也做同样检查。

**Q3：旧数据怎么处理？**
一句话：回填到不可登录的占位用户，新账号看不到。
- `0008_auth.sql` 加 `user_id` 并回填 `usr_legacy`；
- 该用户密码哈希为空，任何登录路径都无法认证；
- 迁移后新行列去掉默认值，漏写 owner 直接失败。

**Q4：JWT 没配 secret 会怎样？**
一句话：启动生成随机临时值，重启后旧 token 全失效。
- 会打 `WARN`；
- 生产必须显式设置 `JWT_SECRET`；
- 当前没有刷新令牌与即时吊销。

## 3. 状态机、幂等与崩溃恢复

**Q1：幂等的三重保障是什么？**
一句话：唯一键、状态 CAS、业务预检查，三层都拦。
- run 幂等键 `(session_id, kind, idempotency_key)` 唯一，重复请求返回原 run；
- `reports.session_id` 唯一 + 生成前查已有报告；
- turn 状态检查 + `state_version` 乐观锁，避免重复答同一题。

**Q2：两个请求同时答同一题会怎样？**
一句话：先锁串行化，再靠状态与版本号兜底。
- Redis/进程锁让同一会话命令排队；
- 后到者看到 `PendingTurnID` 已变或 turn 已回答，返回 `ErrStateConflict`；
- 锁失效时 `UpdateState` 的 `state_version` 仍会拦住。

**Q3：崩溃恢复到什么粒度？**
一句话：恢复到最后一个成功的 run step，不是精确断点。
- `run_steps` 记录节点级产物，重试跳过已完成节点；
- 当前节点会重跑，模型调用可能重复；
- 业务写入有事务、幂等键、唯一约束与 CAS。

**Q4：为什么 `Abort` 可以重复调用？**
一句话：对连点两次取消幂等。
- 已 aborted 直接成功；
- completed/failed 拒绝，避免把完成会话改成中止；
- 状态机是纯函数，容易单测。

## 4. 作答链路与自适应追问

**Q1：模型建议追问，但候选人答全了，听谁的？**
一句话：听规则，覆盖完成优先于模型建议。
- 裁决门顺序固定：时间 → 题纲 → 预算 → 深度 → 单题上限 → 不会 → 降级 → 覆盖 → 模型建议；
- 覆盖判定要求证据引文真的出现在回答里；
- 模型建议只是最后一层偏好。

**Q2：模型输出不是 JSON 怎么办？**
一句话：抽取 + 修复重试 + 降级，面试不中断。
- 先抽第一个 `{` 到最后一个 `}`；
- 失败把错误反馈给模型，最多 2 次；
- 仍失败写降级评估，本题不计分、不追问。

**Q3：10 级追问门是不是过度设计？**
一句话：每一级对应一种真实的失控方式。
- 时间/题纲/预算/深度/单题上限防无限追问；
- 「不会」识别防追问已放弃的人；
- 评估降级防拿坏分数继续追问。

**Q4：为什么评估和提交分两个事务？**
一句话：慢调用不占数据库事务，短事务只做提交。
- 评估可能几十秒，不能持锁等模型；
- 中间崩溃时 `run_steps` 已有评估结果；
- 重试可跳过模型直接提交。

## 5. 报告

**Q1：报告里的总分是谁算的？为什么模型不给分？**
一句话：总分是确定性公式算的，模型只给受约束的维度建议和文字。
- `ComputeScoreWith` 按 rubric 权重、bonus/penalty 计算并可复算；
- 模型不能直接写总分/档位，输出要过长度与 `turn_id` 校验；
- 这样同一份数据每次报告分数一致，可审计。

**Q2：所谓工具回查，是模型自己调工具吗？**
一句话：不是，代码先按固定计划查完，模型只看证据包。
- `Collect` 调 `SessionOverview` / `ListWeakTurns` / `SearchTurns`；
- `ToolCalls` 是审计记录，不是模型自主决策；
- `get_turn` 已实现，但当前采集计划没用它。

**Q3：模型挂了报告还能出吗？**
一句话：能，降级为确定性模板。
- 先构造 `Fallback` 报告，再合并模型输出；
- 非取消类错误保留 fallback，`degraded=true`；
- 只有 context 取消才返回错误留给重试。

**Q4：报告有什么不足？**
一句话：证据包有截断、只有一轮点评。
- 回答摘要、弱项条数、搜索结果都有上限；
- 没有跨场趋势、多轮修订、逐段 critic；
- 报告可信度优先于文采，这是取舍。

## 6. 复习与三种 scoring_mode

**Q1：三种 `scoring_mode` 有什么区别？**
一句话：谁决定 SM-2 排程，取决于评分来源是否客观。
- `objective`：真实模型客观分驱动 SM-2；
- `length_heuristic`：长度估算只作参考，排程按自评；
- `self_only`：没有评估链路，只按自评。

**Q2：没有 key 时复习评分还有效吗？**
一句话：有效的是排程与自评闭环，不是语义客观性。
- 接口与面板明确标 `length_heuristic`；
- 不覆盖历史客观字段；
- 不把长度估算冒充 `objective`。

**Q3：每日上限会改到期时间吗？**
一句话：不改，只裁剪今天展示多少张。
- `REVIEW_DAILY_LIMIT` 默认 20；
- 未展示的卡仍按原 `due_at` 留在队列；
- 接口返回 `deferred_count` / `remaining`。

**Q4：优先级怎么排？**
一句话：高频考点 > 历史低分 > 普通题 > 到期时间。
- 排序在 `Due` 里统一做；
- 每张卡带 `priority` / `sort_reason`；
- 同优先级再按到期时间。

**Q5：为什么 grade<3 要重置？**
一句话：回忆失败说明长间隔失效，明天重来。
- SM-2 lapse 处理：重复次数归零、间隔 1 天；
- 避免把不会的卡越推越远；
- EF 仍会下调，后续间隔更难拉长。

## 7. 简历诊断

**Q1：为什么不用模型直接打分？**
一句话：分数要可复现、可解释、可审计。
- 同一规则版本同一简历必须同分；
- 每个扣分都有规则 ID 与证据；
- `ModelCalled` 恒为 false。

**Q2：红线命中后怎么算？**
一句话：A 维度归零、文档分封顶 69。
- 综合分也不能超过 69；
- 语义是「不能过筛」，不是普通扣分；
- 规则类型写 `redline`。

**Q3：同内容换类型为什么分数不同？**
一句话：规则有类型适用范围和不同画像。
- 实习/项目/工作的扣分与权重不同；
- 类型推不出时进 `needs_confirmation`；
- 不硬猜，避免假精确。

**Q4：为什么不做 OCR？**
一句话：需要另一条成本线，当前明确拒绝而不是静默失败。
- 图片返回 `image_requires_ocr`；
- 扫描版 PDF 提不出文字；
- 让用户改粘贴，比给错分诚实。

## 8. JD 匹配与技能别名归一

**Q1：为什么不上向量库？**
一句话：词表小、封闭、必须可解释，向量检索是刻意取舍。
- 每个命中要能回答是 exact / alias / child / related；
- 向量相似度给不出可复核依据；
- 还要维护语料、索引与阈值，收益不抵成本。

**Q2：四级匹配是哪四级？**
一句话：精确、别名、下位覆盖、弱提示（含编辑距离兜底）。
- `exact` 原文命中，已知 ASCII 技能按 token 边界；
- `alias` 同义双向命中；
- `child` 下位覆盖上位，`parent/sibling/related` 只弱提示、永不计分；
- `fuzzy` 只在 ≥6 字符、同首字母、长度差 ≤1、距离 ≤1 时弱提示。

**Q3：Kafka 能覆盖「消息队列」吗？反过来呢？**
一句话：下位能覆盖上位，上位不能覆盖下位。
- 简历写 Kafka、JD 要消息队列 → 算覆盖；
- JD 要 Kafka、简历只写消息队列 → 不算；
- 这条规则写死在关系表里。

**Q4：Redis 会误命中 Redisson 吗？**
一句话：不会，token 边界 + 保守 fuzzy 阈值。
- 已知 ASCII 技能按 token 边界匹配；
- fuzzy 要求同首字母、长度差 ≤1、距离 ≤1；
- fuzzy 只提示，永不计分。

## 9. 并发、worker 与死信

**Q1：为什么不用 Asynq？**
一句话：PG 已是事实源，队列放同一张库更简单、恢复更一致。
- run、run_steps、租约、业务数据同库，恢复共享事务与观测；
- Asynq 把队列状态挪到 Redis，多一套依赖和状态；
- 当前规模 `FOR UPDATE SKIP LOCKED` + 租约足够。

**Q2：锁 TTL 与长任务怎么处理？**
一句话：锁不跨整个 run，长任务靠 DB 租约和 CAS。
- 生产 worker 模式锁只包住命令临界区；
- run 并发由 `Claim` 的同会话活跃租约互斥；
- 同步内联模式锁跨 run，已加 `Refresh` watchdog 按 `LOCK_TTL/3` 续期。

**Q3：两个 worker 抢同一个 run 会重复执行吗？**
一句话：不会，认领是 `SKIP LOCKED` 的原子 `UPDATE … RETURNING`。
- 两个事务只有一个拿到行；
- 续租/终态写入都带 `lease_id` 条件；
- 旧 owner 醒来也写不进新 owner 的终态。

**Q4：租约过期被接管，会不会重复写 turn？**
一句话：不会写两次业务终态，但模型调用可能重复。
- 从最后一个成功 step 继续；
- 提交有幂等键、唯一约束、`state_version` CAS；
- 外部慢操作不是 exactly-once。

**Q5：死信之后怎么办？**
一句话：人工查、人工重试，没有自动复活。
- `GET /v1/runs?status=dead` 查原因与最后错误；
- `POST …/retry` 显式重试；
- `dead` 重置失败预算，`failed/interrupted` 保留计数。

## 10. 限流

**Q1：为什么 fail-open，不怕被打爆吗？**
一句话：限流后端不是正确性依赖，拒绝整站比暂时失去保护更糟。
- Redis 不可用时放行并打 `WARN`；
- 累加 `rate_limit_degraded_total{action}`；
- 要更严格可改 fail-closed，但那是另一个可用性取舍。

**Q2：为什么按动作拆三个额度？**
一句话：建会话、提交作答、生成报告的成本和滥用方式不同。
- 合并成一个总池会互相拖累；
- 匿名 demo 走更严格的一组；
- 超限统一 429 + `Retry-After`。

**Q3：固定窗口有什么问题？**
一句话：实现简单，但边界处可能双倍突发。
- 当前规模接受；
- 滑动窗口/令牌桶更平滑但状态更多；
- demo 登录仍是进程内计数，多副本要统一到 Redis。

## 11. 可观测性与 trace

**Q1：trace_id 和 request_id 有什么区别？**
一句话：trace_id 是端到端根，request_id 只标识一次 HTTP 请求。
- 客户端不带 trace 头时两者相同；
- 显式透传 `X-Trace-Id` 时是父子关系；
- 日志同时带两个 ID。

**Q2：worker 重启后 trace 不会断吗？**
一句话：不会，trace_id 随 `runs.trace_id` 落库。
- 命令入队时写入；
- claim 与重试从库里恢复；
- 日志继续带同一个值。

**Q3：为什么不用 OpenTelemetry SDK / collector？**
一句话：当前日志 + 可选 OTLP/HTTP JSON 已够定位，额外组件换不来新信息。
- 只有配置 `OTLP_ENDPOINT` 才启用；
- 没配置时零网络、零依赖；
- 导出失败只记 Debug，不影响业务。

**Q4：一次 run 失败怎么定位？**
一句话：指标看分类，trace 查日志，step 看断点。
- `run_failure_total{kind,class}` 找失败类型；
- `grep trace_id=` 串起命令、worker、模型、工具；
- `run_steps` 看最后成功/失败节点。

## 12. 评测

**Q1：没有 key 怎么保证评分有效？**
一句话：没有 key 就不宣称语义有效；能验证的是确定性约束，语义基线必须真实模型。
- heuristic 只验证 schema、证据等硬约束，档位门槛会失败（`eval-v2` 73.3% / 93.3% / MAE 0.66）；
- 真实基线 `eval-v4` 用 DeepSeek 跑 60 条，档位 80.0%、MAE 0.4733；
- 复习侧同样分级，heuristic 不驱动 SM-2。

**Q2：v4 比 v3 好吗？**
一句话：不能简单说好，净效应是档位变差 1 条。
- 档位 81.7% → 80.0%（−1 条）；
- MAE 0.4967 → 0.4733 改善，但主要来自 4 条标注下调；
- 两条实际翻转均为回退，`ai-high-01` 标注修正不计模型改进。

**Q3：四门槛还是五门槛？**
一句话：四条比率/误差门槛 + 一条证据硬不变量。
- schema 100%、档位 ≥80%、相邻档 ≥95%、MAE ≤0.6；
- 证据引用率必须 100%，单独作为硬不变量；
- 因为证据不可定位等于不可用，不是统计指标。

**Q4：80% 门槛是不是太松？**
一句话：真实基线正好贴线，余量很小是主要风险。
- 48/60 再少 2 条就不达标；
- 5 档边界对单维度 ±1 分敏感（79 vs 80）；
- 没有多次跑取众数，60 条样本也偏小。

**Q5：A/B 会偷偷调模型吗？**
一句话：不会，`evaldiff` 与 `/eval` 只读历史 JSON。
- 0 次模型调用、0 费用；
- 只算指标差值与档位翻转；
- 适合回归评审。

## 13. 工程取舍与边界（快问快答）

**Q1：为什么不用消息队列？**
一句话：PG 队列够用，恢复与业务同库。
- `SKIP LOCKED` + 租约 + `lease_id` fencing；
- 不新增中间件；
- 代价是轮询、无优先级/延迟/退避。

**Q2：为什么不引向量库？**
一句话：技能匹配要可解释，词表小且封闭。
- 别名/上下位关系写表里；
- 每个命中可复核；
- 无向量检索是刻意取舍。

**Q3：为什么模型不给总分？**
一句话：总分必须可复算，模型只给受约束的维度建议。
- `ComputeScoreWith` 确定性公式；
- 报告分数与档位不由模型直接写；
- 输出还要过字段校验。

**Q4：为什么 demo 匿名还能隔离？**
一句话：每次 demo 独立 user_id，所有查询按 owner 过滤。
- 不是共享匿名账号；
- 跨账号 404；
- 登录按 IP 限流，业务动作走更严格 Redis 额度。

**Q5：这套系统最薄的地方在哪？**
一句话：真实模型基线贴门槛、评测只跑单次、可观测性停在进程内。
- `eval-v4` 正好 80.0%；
- 5 档边界 ±1 分敏感；
- 指标重启归零，没有 collector/告警。
