## 1. 两套项目经历写法

项目标题建议：

**AI 模拟面试 Agent｜Go 1.25 · cloudwego/eino · PostgreSQL 16 · Redis**

一句话定位：把“简历诊断 → JD 匹配 → 多轮面试 → 复盘报告 → 间隔复习”跑成一条可恢复、可评测的文本面试链路；模型只负责建议和文字，状态、预算、分数、幂等和恢复由确定性代码与数据库负责。

### A. 纯后端岗（Go 后端 / 研发）

1. **控制面 / 数据面分离**：创建、作答、收尾等写命令统一 `POST` 返回 `202 + run_id`（提交即返回任务号，不阻塞等结果），进度由独立只读 SSE 推送；支持 `Last-Event-ID` 断线续播和 15s 心跳，命令与订阅解耦，重连不会重复提交。
2. **行级认领与租约 fencing**：worker 用 PostgreSQL `FOR UPDATE SKIP LOCKED` 原子认领任务，配合 30s 租约、10s 心跳续租；终态写入带 `lease_id` 条件。多实例并行不重复消费，进程崩溃后租约到期可被接管，旧实例醒来也写不回终态。
3. **三重幂等**：`Idempotency-Key` 快路径 + `turns(session_id, seq)` / `reports.session_id` 唯一约束 + 状态机与 `state_version` CAS；重复提交返回原 run 并标 `Idempotent-Replayed: true`，任一层失效仍有数据库兜底。
4. **节点级崩溃恢复**：用 `runs` / `run_steps` 记录每个节点的输入摘要与产物，重启从最后一个成功节点续跑；启动时把超过 60s 未更新的 `running` run 标记为 `interrupted`，避免会话永久卡死。
5. **Redis 锁与限流**：会话锁 `SET NX PX` + token 比较释放，同步内联路径按 `LOCK_TTL/3` 续期（TTL 10s，含 150ms TTL / 600ms 长任务测试）；按「用户 + 动作」拆建会话 / 作答 / 报告三类固定窗口（默认 20 / 120 / 10 每小时，匿名 demo 3 / 20 / 3），超限 429 + `Retry-After`；Redis 不可达时锁回退进程内锁（仅单实例安全），限流 fail-open + WARN + 指标。

### B. AI 应用 / Agent 岗

1. **图编排与规则裁决**：用 eino `compose.Graph` 把一次作答拆成 `snapshot → evaluate → decide → ask_followup / ask_next / END` 的短图，循环由应用层按「一次作答 = 一个 run」驱动；追问由 10 级门裁决（时间、题纲、总预算、深度、单题上限、不会识别、评估降级、要点覆盖、模型建议、兜底），模型只建议、不决定是否继续。
2. **结构化评估与证据回链**：五维打分 + 加减分 + 缺失要点；证据必须在去空白 / 标点 / 大小写后可定位，否则丢弃。建 60 条回归集（Go 35 / AI 25，每条带 `expected_band`、五维人工分与必须可定位的 `evidence_anchor`）和五道门槛；DeepSeek 真实基线 schema 100%、档位 48/60（80.0%）、相邻档 100%、维度 MAE 0.4733、证据 100%，并明确标注 80.0% 贴线、v3→v4 档位净变差 1 条。
3. **RAG 检索**：pgvector + 本地 bge-m3，404 个语义块；54 条检索集（25 原文措辞 / 25 改写 / 4 无答案）。BM25 与向量按 RRF（k=60，词法 1.2 / 向量 1.0）融合，hit@5 0.80→0.84、MRR 0.7123→0.7183，hybrid p50 33ms / p95 43ms；因最佳阈值会误拒 18%–20% 可答问题，不做硬阈值拒答。
4. **工具自主调用**：报告阶段提供 deterministic / autonomous 两种模式，共用只读工具、参数校验和预算；同一会话、同一模型、同一 prompt 对照，autonomous 模型调用 1→3、token 3,170→9,711、耗时 7,959→9,851ms，两臂均 5/5 段、0 降级；结论是「都可用、自主更贵、未取得额外证据」，默认仍走 deterministic。
5. **分层记忆**：结构化状态 + 最近 4 轮原文 + 每 5 轮一次摘要（≤600 字）；10 轮同会话事实回忆从 0/1 提升到 1/1，prompt token 154→632（+478），摘要 427/199、未降级；只做单次开 / 关对照，不做显著性。

## 2. 数字纪律

### 2.1 规则

1. 只写第 2.2 节表里的数字。表里没有的，一律写「待实测」或直接不写。
2. 小数按原文写（如 `0.4733`、`0.7183`），不要四舍五入成 `0.47`、`0.72`；除非明确写「约」。
3. 不要混口径：
   - `band_hit_rate` 是档位命中率；
   - `dimension_mae` 是 1–5 维度的平均绝对误差；
   - `hit@5` / `MRR` 是检索指标；
   - 三臂消融里的 MAE 是 0–100 总分的 MAE，不能和 `dimension_mae` 混用。
4. 不要把「设计参数」写成「实测效果」。例如 30s 租约、10s 心跳、15s SSE 心跳、10s 锁 TTL 都是配置值，不是压测结果。
5. 不要把「单次对照」写成「显著提升」。工具模式、分层记忆都是一次开 / 关对照。
6. 不要把「演示案例」写成「模型指标」。README 里的总分 69、匹配度 77、报告 27.8 是演示数据，不是模型质量。

### 2.6 口径提醒

- **v4 不能写成“比 v3 好”**：档位命中 81.7% → 80.0%，净变差 1 条；MAE 改善主要来自 4 条标注修正；2 条实际翻转都是回退。
- **60 条是单次跑分**：没有多次取众数，样本也偏小；48/60 正好 80.0%，余量为 0（门槛是 ≥80%）。
- **RAG 的 0.0060 差距不显著**：MRR 按 50 条有答案 query 平均，单条 query 的 reciprocal rank 下降 ≥0.30 就足以抹平差距；只能说“不低于”，不能说“优于”。
- **工具模式和分层记忆都是一次对照**：不做显著性；只能说明“机制生效 / 成本变化”，不能说明“普遍更好”。
- **hybrid 的 B 组 MRR 是下降的**：0.5580 → 0.5500，虽然 B 组 hit@5 从 0.64 升到 0.72；不要概括成“各项指标全面提升”。
- **heuristic 结果不能当效果**：`eval-v2`（30 条）的档位 73.3% / 相邻档 93.3% / 维度 MAE 0.66 是 heuristic 回归，只验证 schema 与证据等硬约束，档位门槛会失败；真实基线必须用真实模型。
- **`m20-design.md` 顶部还写着“待评审”**：仓库里已有实现与结果文件，可以写“已实现 / 已评测”，但不要写“生产上线 / 大规模使用”。
- **三臂消融只说「不劣于」，不说「全面更好」**：额度对齐后完整方案 band 71.2% vs 单次 65.0%、MAE 7.86 vs 14.78，两项成立；但 band 最高的是 LLM+RAG（76.7%），完整方案档 5 只命中 2/13，优势集中在档 1/3。首轮基线 `MaxTokens=400` 截断的瑕疵已用 2000 重跑两个基线臂消除，不要把首轮的 66.0% / 15.12 与对齐后的数字混用。

## 3. 一个 STAR 结构的故障故事

### 主故事：自主工具模式第一次全失败——不是模型不会用工具，是我们在模型调用前就把证据喂完了

**S（背景）**

报告阶段原本是确定性的：代码按固定计划调 `SessionOverview`、`ListWeakTurns`、`SearchTurns` 三个只读工具，模型只写点评。后来我加了 `autonomous` 模式，想让模型自己决定查什么。第一次 A/B 对照，自主臂 6 轮全部失败，最后回落到模板报告。

**T（判断）**

当时最容易得出的结论是“模型不会用工具 / 这个模式不可用”。但我先去看审计记录，因为如果模型连一轮工具都没发，问题可能不在模型，而在调用链。

**A（动作）**

发现两个实现缺陷：

1. **输出上限不一致**：自主循环把每轮输出限死在 1,200 token，而确定性模式实测终稿需要 1,213 token，本轮重跑自主终稿实测 1,330 token——1,200 必然截断。修复为两臂共用一个常量 `ReportMaxTokens = 1800`，并加测试以实测 1,213 为下界，防止以后再撞。
2. **启动即预采集**：旧实现 autonomous 启动时仍执行 `Collect`，三件工具在模型第一轮之前就跑完了，模型拿着全量材料直接想写终稿，模型自选工具次数恒为 0。修复为 autonomous 首轮只给“任务 + 可用工具清单 + 会话 id”，证据全部由模型发动作获取；确定性骨架改在模型阶段之后用独立 query 装配，模型不可见。

判定规则是在重跑前写定的：如果 autonomous 同为 5/5 段且无 degraded，结论就是“两种模式都可用”，只比较调用次数、耗时与 token；如果仍 degraded，才写“自主模式不可用”。

**R（结果）**

重跑同一会话、同一模型、同一 prompt：两臂都产出 5/5 段、均未 degraded；自主臂模型自选了 2 个工具（`get_session_overview` → `list_weak_turns`），但这两个工具本来就是确定性采集计划的子集，没有拿到额外证据。代价是模型调用 1 → 3、token 3,170 → 9,711、耗时 7,959 → 9,851ms（约 +24%）。所以结论是“两种模式都可用，自主模式更贵”，不是“自主模式更好”。

**完整口述稿（约 2 分钟；时间紧可只讲 S / A / R）**

> 报告阶段原来是我写死的三次查询，模型只写点评。后来我加了自主模式，让模型自己决定查什么。第一次 A/B，自主臂 6 轮全失败，最后回落到模板。当时最容易下的结论是模型不会用工具，但我先去看审计记录，发现两个实现问题。第一，自主循环把每轮输出限死在 1200 token，而确定性模式实测终稿要 1213，重跑自主终稿 1330，等于一开始就注定截断。第二，自主模式启动时还在跑原来的三次预采集，模型第一轮就拿到了全部证据，它根本不需要选工具，所以“模型自选 0 次”是假自主。我把两臂输出上限统一成 1800，加了一个以实测 1213 为下界的回归测试；自主首轮只给任务、工具清单和会话 id，证据全部由模型发动作获取。重跑同一会话、同一模型、同一 prompt，两臂都是 5/5 段、0 降级；模型自己选了 overview 和 weak_turns 两个工具，但这两个工具本来就在确定性计划里，没有拿到额外证据。代价是模型调用 1→3 次、token 3,170→9,711、耗时 7,959→9,851 毫秒。所以我的结论不是“自主模式更好”，而是“两种模式都可用，自主更贵”。这件事让我记住：先证明机制真的发生，再比较效果。

### 备选故事（纯后端岗可替换）

**锁 TTL 与持有时长不匹配**：`LOCK_TTL` 默认 10s，而报告生成、真实模型评估可能远超 10s。生产 worker 路径下命令入队后立即释放锁，run 在锁外执行，所以默认不触发；但同步内联执行模式下 run 在锁内执行，10s TTL 会让锁中途失效，第二个命令可以拿锁进入，锁的互斥承诺静默失效。修复：`ports.Locker` 增加 `Refresh`（仅当前 token 可续期，失去所有权返回 `ErrLockBusy`）；同步内联路径启动 watchdog，按 `LOCK_TTL/3` 续期，失去所有权时记录 `session lock lost during inline run`；测试用 150ms TTL + 600ms run 证明长任务期间第二个 token 拿不到锁。结论：锁的 TTL 必须和临界区长度绑定，执行模式一变，锁的语义会静默改变。

## 5. 5 个最可能被追问的点 + 30 秒应答骨架

**Q1：两个请求同时答同一题会怎样？**

- 先用会话锁把同一会话的命令串行化；
- 后到者看到 `PendingTurnID` 已变或 turn 已回答，返回 `state_conflict`；
- 锁失效时还有 `state_version` CAS 和唯一约束，不会写出第二份。

出处：[project-walkthrough.md](project-walkthrough.md) §3、[interview-qa.md](interview-qa.md) §3。

**Q2：为什么把队列放 PostgreSQL，不用 Kafka / Asynq？**

- PG 已经是事实源，run、`run_steps`、租约和业务数据同库，恢复与提交共享事务；
- 认领用 `FOR UPDATE SKIP LOCKED` + 租约 + `lease_id` fencing，多实例不重复、崩溃可接管；
- 代价是轮询、无优先级 / 延迟队列 / 指数退避，当前规模够用，变大再换。

出处：[project-walkthrough.md](project-walkthrough.md) §10、[interview-qa.md](interview-qa.md) §9。

**Q3：模型建议追问，但候选人已经答全了，听谁的？**

- 听规则：覆盖门排在模型建议之前；
- 证据引文必须真的出现在回答里，不能由模型编“已覆盖”；
- 模型只建议，10 级门保证预算和停止条件可单测。

出处：[project-walkthrough.md](project-walkthrough.md) §4、[interview-qa.md](interview-qa.md) §4。

**Q4：报告里的分数和工具，是模型做的吗？**

- 分数由 `ComputeScoreWith` 确定性公式算，模型只写点评，输出还要过长度和 `turn_id` 校验；
- 工具默认 deterministic，代码按固定计划采集；autonomous 只是 opt-in，首轮只给任务、工具清单和会话 id；
- 实测 autonomous 模型调用 1→3、token 3,170→9,711、耗时 7,959→9,851ms，两臂都 5/5，所以只说“都可用、自主更贵”。

出处：[project-walkthrough.md](project-walkthrough.md) §5、[interview-qa.md](interview-qa.md) §5、[tool-mode-compare-v2](eval-results/tool-mode-compare-v2.json)。

**Q5：检索为什么不做硬阈值拒答？RRF 为什么是 1.2 / 1.0？**

- 54 条上无答案和有答案分数重叠，最佳阈值能拒 4/4 无答案，但误拒 10/50 可答（20%）；
- RRF 只试了 1.2 / 1.5 / 2.0，1.2 是 A 类 hit@5 与 MRR 不降的最小加权，总 MRR 0.7100→0.7183；
- 但比 BM25 只高 0.0060，单条 query 名次变化就能抹平，所以结论只能写“不低于”，不能写“优于”。

出处：[design-rationale.md](design-rationale.md) §13 / §14、[interview-qa.md](interview-qa.md) §12。

## 6. 投递时的取舍建议

- **纯后端岗**：用 A 套 5 条，项目标题保留 Go + PostgreSQL + Redis；不要在标题里写“AI Agent”作为第一关键词，把“后端可靠性”放前面。
- **AI 应用 / Agent 岗**：用 B 套 5 条，标题保留 eino + RAG + 工具自主；纯后端那套里的队列和幂等可以压缩成 1 条补充，不要两套全部贴上去。
- **两套都投时**：同一份简历只选一套；另一套留在面试口述里，不要在同一份简历里堆 10 条。
- **没有数字的能力**：只写设计，不写效果；面试官追问时主动说“这块没有压测 / 没有显著性”，比硬编数字可信。
